\subsubsection{Resource monitoring}
\label{sec:m6-resources}
\guidance{

We watch the running system from two places (EDN-99, \href{https://github.com/mlops-2627q1-mds-upc/MLOPS_Recommenditos/issues/224}{\#224}).
Inside the Compose stack on the VM, Prometheus scrapes the API's own metrics, cAdvisor for each container's memory, CPU, and restarts, and node-exporter for the host's memory and disk, every 15 seconds; it keeps at most 2\,GB or 60 days, so that its storage cannot fill the disk (NFR-04).
From outside, Better Stack requests the public \texttt{/health} every 3 minutes, because a monitor on the VM cannot report the VM itself being gone (EDN-10, \href{https://github.com/mlops-2627q1-mds-upc/MLOPS_Recommenditos/issues/226}{\#226}).
From 2026-11-04 to 2026-11-05 it recorded 100\,\% availability and no incident (\texttt{reports/\allowbreak uptime/\allowbreak availability.json}); the 5 seconds of 503 a deploy causes open no incident, since Better Stack opens one only when a failure lasts through its 3-minute confirmation period (\cref{sec:m6-feedback}).
Grafana shows the figures on a provisioned dashboard, each against the limit a requirement sets, and is reachable only through an SSH tunnel, so that nothing new is public (EDN-99, \href{https://github.com/mlops-2627q1-mds-upc/MLOPS_Recommenditos/issues/225}{\#225}).

\Cref{tab:m6-risks} lists the failures we expect on one VM with one vCPU, 4\,GB of memory, and no swap, and what reports each.
Fourteen Prometheus alerting rules post through Alertmanager to the team's Discord channel.
Every message carries what to do, from the runbook in the monitoring documentation, and a link to its dashboard panel, and every rule has unit tests (\texttt{promtool test rules}) for the series that must fire it and those that must not.
A latency or error alert fires only when the share over the last minute stays above the target for 5 minutes, with at least 20 answers a minute: a share over 5 minutes would fire after a spike shorter than a minute, such as the CPU spike of a drift pass on the one vCPU, and post a firing and a resolved message for nothing.

\Cref{fig:m6-service-health} shows the dashboard during a run of NFR-03's load test, 20 requests per second for five minutes, against the VM with the full stack running (\href{https://github.com/mlops-2627q1-mds-upc/MLOPS_Recommenditos/blob/main/reports/loadtest/vm-2026-11-05-full-stack.md}{\texttt{reports/loadtest/}}).
The rate was reached and none of the 6,013 requests failed, so NFR-03's rate and error targets hold with the monitoring added.
The API used 64\,\% of the vCPU on average and the seven other containers together less than 2\,\%; the API's memory peaked at 303\,MiB of its 768\,MiB limit, and the disk had 12.1\,GB free.
NFR-02 was not re-run with the full stack by the method EDN-88 decided, a Locust test on the VM: this run's client was on a laptop, and its p95 of 280\,ms for \texttt{/v1/predict} includes the internet and nginx, so it does not measure NFR-02.
The API's own histogram supports the target: 97.1\,\% of the 3,607 \texttt{/v1/predict} answers took at most 250\,ms inside the API, a p95 of 218\,ms, which is a lower bound of what a client on the VM sees.
The drift job, outside this window, takes 5 to 7 seconds per pass, and its highest 15-second memory sample during the replay of \cref{sec:m6-model-performance} was 225\,MiB of its 512\,MiB limit.

The same run shows what the dashboard cannot see.
Locust measured a p99 of about 1\,s, while the API took more than 750\,ms for only 17 answers: its histogram starts when the API receives a request, so time in the network, nginx, or the socket backlog is outside it.
The latency alerts need 20 answers a minute, so a slow API without traffic stays unnoticed, and when Prometheus or Alertmanager is down only Better Stack still notices an API that does not answer.

\subsubsection{Model performance}
\label{sec:m6-model-performance}
\guidance{
  \textbf{Template:} e.g.\ Alibi Detect.\\
  \textbf{Rubric (5 pts):} To what extent does our monitoring provide timely, actionable signals about data changes, model performance degradation, and user impact?\\
  \textbf{Lecturer feedback:} show the signal itself, the drift job's output on the Spanish replay, and what a person did with it; the lecturer praised arguing a choice from measured criteria and their cost (lgbm-basic, SC-06, and energy in the first report).
}

The system has no real users, so its traffic is a replay of held-out listings that a person starts on the VM (EDN-100, \href{https://github.com/mlops-2627q1-mds-upc/MLOPS_Recommenditos/issues/227}{\#227}).
It sends listings to the API as a client would and posts each listing's real price to the feedback endpoint (FR-10), so the prediction log holds both the requests and their labels.

\paragraph{Data changes.}
A drift job runs every 15 minutes in its own container and tests each new window of 1,000 logged requests against 10,000 training listings (EDN-101, \href{https://github.com/mlops-2627q1-mds-upc/MLOPS_Recommenditos/issues/228}{\#228}).
Each of the 23 features gets its own Alibi Detect test: \texttt{KSDrift} for the eight numeric ones and \texttt{ChiSquareDrift} for the seven categorical ones and eight missing-value indicators.
A window is flagged when any feature is below $p = 0.005/23$ (NFR-11, EDN-14, which absorbed EDN-26 and EDN-29).
We measured these settings before building the job: windows of 100 requests show three drifted features in at most 82\,\% of trials, and the usual level of 0.05 would make the false-alarm rate equal to the 1 in 20 control windows NFR-11 allows.
\texttt{model} is left out, because its 349 levels are too many for a chi-square test on 1,000 requests.
The job stores every window with each feature's p-value in SQLite, so a finding can be investigated after the fact, and exports the latest window to Prometheus.

\paragraph{Performance degradation and user impact.}
To see whether users get worse prices, the job also computes the real MdAPE and the share of price ranges that hold the price, from the observed prices of a window's own requests (\href{https://github.com/mlops-2627q1-mds-upc/MLOPS_Recommenditos/issues/229}{\#229}).
It reports the MdAPE only with at least 200 labelled answers and the coverage only with at least 300 labelled ranges, so that a window whose prices have not arrived shows no value instead of a good one.
The MdAPE is compared with the test MdAPE, and the coverage with the nominal 90\,\% the ranges promise; for the model the replay below ran against, before the retrain of \cref{sec:m6-feedback}, these were 6.73\,\% and 90.2\,\% on the test set.
Each alerts at a one-sided level of about 0.005 per window, the false-alarm level of NFR-11 (\href{https://github.com/mlops-2627q1-mds-upc/MLOPS_Recommenditos/issues/230}{\#230}): \texttt{ModelErrorHigh} above $1 + 3.52/\sqrt{n}$ times the test MdAPE, \texttt{ModelCoverageLow} more than 2.576 standard errors and a continuity correction below the nominal 90\,\%, with $n$ the window's labels.
At 1,000 answers and 500 ranges these are 7.48\,\% and 86.44\,\%.
\texttt{DriftDetected} names the drifted features.
Each alert's runbook step ends in the Retrain workflow of FR-15, with the job's finding as its reason; a person starts it (EDN-12).

\paragraph{The replay on the VM.}
On 2026-11-04 from 22:26 to 23:03 UTC, the replay sent 5,000 control listings and then the 5,779 of the 6,079 listings of the Spanish (\texttt{ES}) holdout that the API accepts, a market the model never saw (\cref{fig:m6-replay}; data in \href{https://github.com/mlops-2627q1-mds-upc/MLOPS_Recommenditos/blob/main/reports/monitoring/vm-es-replay-2026-11-04.md}{\texttt{reports/monitoring/}}).
No control window was flagged, and every \texttt{ES} window was, in 13 to 15 of the 23 features.
Their MdAPE of 9.0 to 9.4\,\%, 1.33 to 1.40 times the test MdAPE, is above the ceiling in every window, and their coverage of 85.4 to 87.6\,\% falls below the floor in two of the five.
The control windows' MdAPE of 4.9 to 5.4\,\% and coverage of 95 to 97\,\% are not a baseline, because the control listings are training listings and their figures are in-sample.
The first \texttt{ES} window was flagged by the pass that ended 3.5 minutes after the window filled, 7 minutes after the first \texttt{ES} request; in general, a signal comes at most 15 minutes after the 1,000 requests of a window have arrived, so its delay is the time the traffic takes to fill a window plus at most 15 minutes.

The model alerts were deployed after the replay, so only its last window reached Alertmanager: \texttt{DriftDetected} and \texttt{ModelErrorHigh} fire, and \texttt{ModelCoverageLow} stays quiet at 86.6\,\% against the floor of 86.44\,\%.
The coverage alert is the weakest of the three signals at 500 ranges, and drift and error both cover the windows it misses.
These known findings were silenced until the retraining rehearsal of \cref{sec:m6-feedback}.

\paragraph{The control clause of NFR-11.}
\texttt{monitoring/tests/test\_nfr11.py} runs the job's own pass over 20 control windows and the first \texttt{ES} window of the versioned samples, and requires at most one flagged control window and the \texttt{ES} window flagged in at least three features besides \texttt{country\_code}.
It needs the DagsHub credentials, which only \texttt{main} has (EDN-91), so CD runs it before any image is pushed, and it passed on the last release, of 2026-11-05.
When the test was written, on the samples of 2026-11-04, no control window was flagged, and the lowest p-value of any control feature was 0.0035, 16 times the threshold.

\paragraph{What the dashboard cannot show.}
\Cref{fig:m6-replay} is drawn from the job's own store, because Prometheus holds only the latest window a pass tested.
Real users would send prices late or never; the job recounts a window for 7 days, and the dashboard's label counts show why a figure is missing.

\paragraph{The stages.}
The observed prices reach only the monitor: no pipeline stage reads the prediction log, so a retrain learns from the versioned dataset, and in the rehearsal what changed was the split of \href{https://github.com/mlops-2627q1-mds-upc/MLOPS_Recommenditos/pull/300}{\#300}, prepared before the finding.
The Retrain workflow runs only from \texttt{main} and only when a person starts it (EDN-92).
On a GitHub-hosted runner it runs \texttt{dvc repro}, logs the runs to MLflow on DagsHub, pushes the artefacts to the DVC remote and the new \texttt{dvc.lock} to a branch, and its summary gives the gate verdict and a link that opens the prefilled promotion pull request.
A person opens that pull request and, after a review, merges it, which promotes the model; a required check blocks the merge unless the committed \texttt{metrics.json} says the gate passed for the model \texttt{params.yaml} promotes, so a rejected model cannot be merged by mistake.
The merge to \texttt{main} starts CI, then CD, which bakes the model into the image (EDN-08) and runs NFR-11's test on the new monitoring samples before it pushes, then Deploy, whose smoke check holds \texttt{/health} to the model version that \texttt{dvc.lock} records and puts the previous release back when it fails.
A rollback is the same Deploy workflow started with the previous release tag.
Automating the whole loop would need a trigger that starts Retrain on an alert and a step that opens and merges the promotion pull request when the gate passes; the gate and the required check already stop a rejected model.
EDN-12 keeps a person at both points instead.

\paragraph{The recovery criterion.}
We posted the criterion on \#231 before any run and report against it unchanged (\cref{tab:m6-recovery}).
Points 1 and 3 pool the two \texttt{ES} windows with the drift job's own formulas; point 2 is the paired comparison of both models on all 2,266 held-out \texttt{ES} listings, from the dry run of \#300, which applies to the promoted model because its booster and interval files are the same files.
Point 3a is not paired: the replay alternates price and range requests, and the \texttt{ES} phase started at an odd position before and an even one after, so 84.3\,\% and 88.5\,\% come from the two halves of the same 2,000 listings.

The recovery criterion is not met in full: points 1 and 2 hold, and point 3 holds for coverage, but \texttt{ModelErrorHigh} and \texttt{ModelCoverageLow} still fire on one of the two \texttt{ES} windows.
Window 18's MdAPE of 7.82\,\% is 1.149 times the test MdAPE, above the ceiling of 1.111 at 1,000 labels, and its coverage of 86.40\,\% is below the floor of 86.44\,\%; window 17, at 7.49\,\% and 90.6\,\%, fires neither.
The cause is the baseline: the ceiling is relative to the overall test MdAPE of 6.80\,\%, while \texttt{ES} on the test set itself is at 7.61\,\%, 1.12 times that, so an \texttt{ES} window at the model's own \texttt{ES} error sits at the ceiling.
\href{https://github.com/mlops-2627q1-mds-upc/MLOPS_Recommenditos/issues/306}{\#306} follows this up by judging a window against its market's baseline.
\href{https://github.com/mlops-2627q1-mds-upc/MLOPS_Recommenditos/issues/307}{\#307} tracks a second weakness the rehearsal showed: a window that is not final is scored again on every pass against the test values of the running release, so after the promotion the windows of the old model read against 6.80\,\% instead of the 6.73\,\% they were judged on.
Drift stays flagged after the promotion, as the criterion expected: the \texttt{ES} inputs still differ from a reference that is 3.8\,\% \texttt{ES}, and the job tests inputs, not error.
